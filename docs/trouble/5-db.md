## 1. What Went Wrong (Root Causes)

### A. Lazy Evaluation & Late-Surfacing Python Errors

* **What happened:** When updating `backend/app/models/models.py`, a minor typo (`from datetime import dat`) and a missing import (`import enum`) were introduced.
* **Why it caused a headache:** Python uses **lazy loading** for module parsing. A file isn't checked for syntax or missing variables until something actually imports it. The errors didn't show up immediately when editing the file; they only triggered when Alembic's `env.py` loaded `models.py` during migration autogeneration.

### B. SQLite’s Strict DDL Limitations (`ALTER TABLE` Syntax Error)

* **What happened:** When Alembic autogenerated the migration script, it produced standard SQL statements like `ALTER TABLE assignments ALTER COLUMN status TYPE TEXT`. When running `alembic upgrade head`, SQLite threw a syntax error (`near "ALTER": syntax error`).
* **Why it caused a headache:** **SQLite does not support direct column alterations, type changes, or constraint drops** via standard SQL. Unlike PostgreSQL or MySQL, SQLite requires all structural modifications to be wrapped in Alembic's **batch mode** (`op.batch_alter_table`), which recreates the table safely under the hood.

### C. Migration Branching & Duplicate Heads

* **What happened:** Because the first migration attempt failed midway (leaving the `teams` table partially created in `caseloop.db`), subsequent re-runs and re-generations created a second conflicting migration file (`4f375b1530b0` alongside `85daa8c7a156`).
* **Why it caused a headache:** Alembic detected multiple competing heads stemming from the same parent revision (`1b86f570ca4e`), throwing `Target database is not up to date` and `table teams already exists` errors because the database state and the migration history files were out of sync.

## 2. Quick Troubleshooting & Prevention Guide

When working with FastAPI, SQLite, and Alembic, keep this checklist handy to avoid similar speedbumps:

### Rule 1: Always Use Batch Mode for SQLite Migrations

If your database URL points to SQLite (`sqlite:///...`), never leave autogenerated `op.alter_column()` or `op.drop_column()` statements sitting in the root of `upgrade()` or `downgrade()`. Always ensure they are wrapped inside:

```python
with op.batch_alter_table('table_name', schema=None) as batch_op:
    batch_op.alter_column(...)
    batch_op.drop_column(...)

```

### Rule 2: Keep Migration History Linear

Avoid generating multiple conflicting revision files for the same schema change.

* If a migration fails halfway, **downgrade** back to the stable revision (`alembic downgrade -1`), delete the broken version file in `alembic/versions/`, fix your model code, and generate a fresh migration once.
* Use `alembic history` to inspect your revision chain and `alembic current` to check what version your database currently acknowledges.

### Rule 3: Validate Models Before Migrating

Before running `alembic revision --autogenerate`, quickly verify your `models.py` file:

* Confirm all third-party types (`enum`, `datetime`, etc.) are explicitly imported at the top.
* Ensure relationship names (`back_populates`) match exact table model names.
